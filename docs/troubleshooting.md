## 诊断脚本

| 命令 | 用途 |
|---|---|
| `python _diag_gateway.py --chat` | 依次检查：端口在不在监听 → `/health` → `/v1/models` → 一次真实的流式对话，告诉你断在哪一步。用 `--port` / `--key` / `--model` 指定参数 |
| `python _diag_campaign.py` | 检查每个账号的签到 / 活动资格：机器身份、本机虚拟化状态、套餐额度、活动列表、成就。只读，不会领取任何奖励。`--uid` 只看一个账号，`--no-local` 跳过虚拟化检查 |
| `python _verify_models.py --base http://127.0.0.1:8790` | 逐个对比网关的模型清单和官方数据。退出码 0 表示一致，1 表示有差异，2 表示网关不可达 |
| `python scripts/risk_diag.py` | 只读诊断账号池健康、排队 / 风控信号和当前生效的开关，默认不发任何上游请求；加 `--probe` 额外探测一次网关域名的连通性 |

## 常见问题

### 客户端一直显示「工作中」，没有任何输出，网关日志也没有变化

大多数情况是网关根本没在运行，请求没有到达网关。先运行 `python _diag_gateway.py --chat` 确认。

- **Windows**：`start-qoder-proxy.bat` 在后台运行。查看 `qoder-proxy.log` / `qoder-proxy.err.log`；再次运行启动脚本会提示服务是否已经在运行
- **Linux / macOS / 局域网脚本**：在前台运行，关闭终端服务就停止了
- 如果日志的时间戳停在某一时刻，之后再也没有出现 `POST /v1/chat/completions`，说明网关已经停止

### 连接被拒绝（WinError 10061）、超时或连接重置

错误信息里会写出目标地址和排查建议。常见原因：

- 设置了 `HTTPS_PROXY` 等代理环境变量，但对应的代理软件已经关闭
- 端口或地址填错了

注意网关不读取 Windows 系统代理，见[出口代理](deployment.md#出口代理)。

### 返回 401 / 400 / 403 / 413 / 430 / 503

| 响应 | 原因 |
|---|---|
| `401 invalid api key` | Key 不对，或者已经停用 / 删除 |
| `401 panel password required` | 访问管理接口但没有登录面板 |
| 所有请求都被上游 401，账号却是正常的 | 多半是机器时钟不准：COSY 签名带时间戳，偏差超过 120 秒就会失败。看 `/health` 的 `env.clock_skew_s`，同步系统时间 |
| `400`，提示模型和出口不匹配 | Key 绑定的区域没有这个模型，见[双区路由](models.md#双区路由) |
| `403`，查看明文 Key 时 | 面板仍在用默认密码，先修改密码 |
| `413`，提示 `payload too large` | 请求编码后超过上游网关的大小限制（`QD_MAX_BODY_MB`，默认 29MB），网关在本地拦下、没有发出。常见于一次带很多图片，或长对话里累积了大量历史图片。减少图片数量 / 尺寸，或开一个新会话 |
| `430 version_too_low` | 上游要求升级客户端版本，与账号或网络无关。升级网关到最新版 |
| `503 no usable account` | 当前区域没有可用的账号。去看板添加或启用账号 |

### 聊天一直排队，或频繁 10605 / 429

这是上游的风控和容量控制，不是网关故障。网关会按 `retryAfterSeconds` 自动等待重试（默认最多 6 轮、共 10 分钟）。可以按以下顺序排查：

1. 运行 `python scripts/risk_diag.py`，或查看 `/health` 的 `risk` 字段，确认是排队、限流还是拒绝
2. 在容器或数据中心出口上使用国际版账号，最容易被排队。考虑换住宅出口，或改用国内版
3. 同一账号并发过高时，设 `QD_TRAFFIC_GUARD=on` 限制每个账号的并发和请求节奏，见[流量守卫](configuration.md#流量守卫)

原理和更多处置办法见[风控与排队](risk-control-and-queueing.md)、[风控处置手册](risk-control-playbook.md)。

### 内容安全审核拒绝（`content_policy_rejected`）

上游的内容审核判定输入不当。这是确定性的结果，重试没有用，需要修改或缩短输入内容。

### 显示「签到成功」，但积分没变；或者看不到活动

1. 运行 `python _diag_campaign.py`，查看每个账号的活动列表和不可领取的原因
2. 对照[官方活动规则](accounts.md#官方活动规则)：每日活动按「人」去重，虚拟机环境、批量注册的账号、从未登录过桌面客户端的账号，都可能看不到活动
3. 国际版需要真实机器身份，见下文[已知限制](#国际版签到需要真实机器身份)

### 余额长时间不更新

余额只在账号被使用后，才会在后台刷新（默认每 5 分钟一次）。账号行会显示余额的更新时间。想立即刷新，点看板账号页的「刷新积分」。

## 已知限制

### 国际版签到需要真实机器身份

国际版的活动接口会严格校验 `Cosy-MachineToken` / `MachineCode` / `MachineType`。这套身份必须由官方 UMID 组件生成，派生出来的假身份会导致活动被整条过滤掉。所以拿不到真实身份时，网关不会发送这组请求头，并在活动状态里标注 `machine_headers=omitted`。

- **Windows**：使用桌面客户端自带的组件，安装官方桌面客户端即可；不想装客户端时，也可以运行 `python _install_umid.py` 提取 `runtime-info.exe` + `sgsdk.dll`
- **Linux / macOS**：运行 `python _install_umid.py`，从官方 npm 包中提取组件（会校验 sha512，不需要 node）
- **Docker**：镜像构建时已经提取好

国内版没有这个限制，只需要基础的客户端请求头。

### 同一台机器上的多个国际版账号无法都领到每日活动

UMID 组件输出的是**机器级**身份，与账号无关。上游按设备去重，所以同一台机器每天只有一个账号能领。而且活动是否下发，由登录官方客户端的那台机器决定，网关无法为其他账号「制造」出活动。想让多个账号都能领，需要多台物理机器。

### 虚拟化检测有误报

官方组件的 `isVm` 是纯机器指纹，对所有账号返回同一个值。开启了 VBS / HVCI 的 Windows 11 实体机、部分 Linux 实体机，都会被判定为虚拟机。根据官方条款，这会导致新号拿不到新人 300 Credits。`vmInfo` 只用于本地诊断，网关不会上报。

### 自建 alpine 镜像需要 glibc 兼容层

提取出来的 UMID 组件是 glibc 动态链接的程序，在 musl 系统上无法直接运行（报 `exit 127`，看起来像是文件不存在）。官方镜像已经安装了 `gcompat libstdc++ libgcc`；自己构建镜像时也要装上。组件存在但无法执行时，stderr 会打印一次 `[runtime-info] 无法执行 …`。

### Anthropic 入口的差异

没有 thinking block、流式出错时不重试等，见[客户端接入 · Claude Code](clients.md#claude-codeanthropic-messages)。

### 容器中的设备身份

只要 `accounts/` 挂载为卷，容器重建后身份不变；如果不挂载，每次重建都会换一个身份。详见[容器里的设备身份](deployment.md#容器里的设备身份)。
